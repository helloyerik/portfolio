## Summary
Внутри корпоративного портала я работал над несколькими модулями, связанными с внутренними процессами компании. Основной фокус был на двух направлениях: управление сотрудниками и оргструктурой, а также документы с маршрутом согласования и подписания через eGov.

Это был не один экран, а набор связанных инструментов для разных ролей: сотрудника, руководителя, HR и администратора. Задача состояла в том, чтобы перевести внутренние процессы в понятный цифровой интерфейс и заложить фундамент для масштабируемого внутреннего продукта.

Отдельной сложностью было то, что часть модулей приходилось проектировать без полноценной входной документации. Поэтому работа шла через короткий этап discovery, сбор данных, интервью со стейкхолдерами и модульную структуру решения.

## Results
- спроектировал несколько модулей корпоративного портала в условиях неполного ТЗ
- собрал модуль документов с маршрутами `list / new / edit / process`
- выстроил ролевую модель процесса: инициатор, согласующий, подписант, наблюдатель
- подготовил интерфейс и логику под интеграцию с eGov для электронного подписания
- связал интерфейс документов со state machine процесса и статусами
- заложил основу для админского слоя сотрудников и ручного управления оргструктурой
- помог привести проект к презентации итогов года, после чего на него выделили дополнительный бюджет

## Контекст
Проект начинался без подробного ТЗ и вводной документации. Нужно было быстро понять, какие внутренние задачи реально нужно решать, где проходят границы между ролями и какие модули важнее спроектировать в первую очередь.

Из-за жесткого срока было важно не пытаться сразу довести все до максимальной глубины. Вместо этого проект был собран как модульная система: сначала устойчивый фундамент, затем последовательное углубление в отдельные части.

## Модуль 1. Управление сотрудниками
Этот модуль был связан с административной частью портала. Здесь нужно было дать компании базовый интерфейс для управления сущностями сотрудника и ручного связывания данных, которых не было в ЗУПе.

### Сущности
- сотрудник
- подразделение
- структура
- должность
- специализация должности

### Функциональность
- редактирование подразделения сотрудника
- редактирование начисления коинов
- поиск по профилям для всех пользователей
- создание структуры
- возможность задавать логин и пароль пользователю

### Экранный сценарий
- при входе в админку открывается список пользователей
- в строке пользователя: фамилия, имя, номер телефона, должность
- при выборе пользователя открывается карточка сотрудника
- внутри карточки: фамилия, имя, отчество, корпоративная почта, новый пароль, подтверждение пароля
- ниже отдельный блок оргструктуры, где сотрудника можно вручную привязать к подразделению
- внизу действия: `Сохранить`, `Применить`, `Отменить`

### Почему модуль важен
Этот модуль нужен был не только как CRUD-интерфейс. Он закрывал проблему отсутствующих связей между сотрудником и реальной внутренней структурой компании, которую нельзя было надежно подтянуть автоматически из существующих систем.

## Модуль 2. Документы и eGov
Второй крупный модуль был связан с маршрутами согласования и электронного подписания документов. Документ создается как часть бизнес-процесса, после чего проходит несколько этапов: согласование руководителем, проверка HR и финальное подписание через eGov.

### Роли
- сотрудник создает документ через бизнес-процесс
- руководитель согласует или отклоняет заявку
- HR проверяет документ и отправляет его на подписание
- подписанты завершают процесс через eGov

### Что включает модуль
- список документов / процессов
- создание нового процесса
- редактирование процесса
- карточка процесса
- статусы и этапы
- действия по ролям
- подготовка под eGov signing flow

### HR-сценарий
- табличный список процессов с колонками: ID, тип документа, ФИО сотрудника, дата создания, статус, действия
- фильтрация по статусам
- поиск по ФИО и типу документа
- открытие превью документа
- действия: `Отправить на подписание`, `Вернуть на доработку`
- модальное подтверждение при отправке

### Сотрудник
- список всех созданных документов
- тип, дата, текущий статус
- просмотр документа
- индикатор текущего этапа процесса

### Руководитель
- список заявок на согласование
- просмотр документа перед решением
- действия: `Согласовать` / `Отклонить`

## Что было важно в UX
- статусы и этапы должны считываться сразу
- роли должны видеть только релевантные действия
- процесс должен быть понятен и в списке, и внутри карточки
- состояние eGov-подписания нужно визуализировать как отдельный слой
- поиск и фильтрация особенно критичны для HR-сценария

## Что показывает этот кейс
- умение проектировать внутренние продукты, а не только B2C-сценарии
- умение делить большой внутренний проект на модули
- умение собирать интерфейс вокруг ролей, статусов и процесса
- умение закладывать основу под backend-контракт и state machine
- умение двигать проект даже при неполной входной документации
